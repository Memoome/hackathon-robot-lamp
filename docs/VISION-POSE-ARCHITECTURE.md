## 1. 已定决策

| 项 | 决定 |
|---|---|
| 端侧（ESP32-S3）模型 | 只跑 Espressif 官方 `pedestrian_detect` / `PICO_S8_V1`（224×224，人体框 + 置信度，无关键点） |
| 姿态模型位置 | 电脑端（作为“云端”）；端侧不再跑姿态模型 |
| 电脑端姿态模型 | Ultralytics **YOLO26-pose**，默认 `yolo26s-pose`，可切 `yolo26m-pose`；本阶段不考虑许可证 |
| 图传通道 | USB 与 WiFi 都做，**默认 USB**；两条通道使用同一套消息格式 |
| 跟随 | 只依赖端侧检测框，电脑离线时照常工作（跟随/舵机闭环本身是后续任务） |
| 摄像头视角 | 正对用户（台灯在桌上，桌面遮挡腰以下） |
| 识别的状态 | 共 9 种：端侧 4 种（离座/回来、久坐、离太近、起身站立），电脑端 5 种（低头、歪头、肩膀一高一低、伸懒腰、趴桌），定义见第 6 节 |
| 分类方式 | 全部先用规则 + 个人校准基线 + 时间防抖，不先训练模型；系统运行中积累关键点与人工标注，规则不够准的类别再训练小分类器 |
| 电脑→板回传 | 回传结构化的姿态 JSON（状态码 + 等级 + 指标），不是给人看的中文句子 |
| 暂缓 | 画面偏粉/过曝（AWB 或 IR-cut 问题）、跟随舵机闭环 |

选择依据（实测）：
- 端侧 PedestrianDetect 推理 117.4–121.7 ms，均值 118.2 ms（6 次），与官方 118.3 ms 一致；有人时置信度 0.83–0.91。
- 端侧 YOLO11n-Pose 推理约 7.24 s，同期置信度 0.32–0.56，不适合实时。
- YOLO26-pose 在 COCO 关键点上各尺寸都优于 YOLO11-pose（官方 mAP50-95：n 57.2 vs 50.0，s 63.0 vs 58.9，m 68.8 vs 64.9）；输出同为 COCO 17 点，现有 `pose/live/host/posture.py` 可直接使用。注意该成绩来自 COCO 清晰大图，本项目 240×320、偏色的画面上差距未经验证。

## 2. 总体架构

```
┌──────────────── ESP32-S3（常驻）────────────────┐        ┌──────────── 电脑（按需）────────────┐
│ BF3901 240×320 UYVY，连续开流                    │        │                                      │
│   └─ 每帧：UYVY→RGB → PedestrianDetect ~118ms    │        │  传输层：USB 串口 / WiFi（同一消息格式）│
│        ├─ DET 事件（框、置信度、中心）──────────────┼─USB/WiFi→ 网页实时显示检测结果              │
│        │     └→ 板上跟随（后续任务，不依赖电脑）     │        │                                      │
│        └─ 触发姿态时：同一帧 UYVY → JPEG ─────────┼─USB/WiFi→ 解码 → YOLO26-pose → 17 关键点   │
│             附带帧号与检测框                        │        │   → posture.py 坐姿判断 → 网页 / API  │
│                                                  │ ←──────┼─ 可选回传 POSE 结果（供后续台灯动作）   │
└──────────────────────────────────────────────────┘        └──────────────────────────────────────┘
```

两条数据流：
1. **检测流（高频、小包）**：每帧一条检测结果，几十字节，用于实时显示和跟随。
2. **姿态流（低频、大包）**：仅在触发时发送一帧完整画面的 JPEG，电脑端做关键点和坐姿判断。

## 3. 端侧固件设计

在现有 `pose/live/firmware/main/` 基础上修改。

### 3.1 连续检测循环（替换现在的“一问一答”取帧）

现状（实测，单帧约 2.0 s）：每条命令都重新配置寄存器（约 0.4 s）、开流并丢 5 帧预热（约 0.45 s）、十六进制传 120×160 预览（约 1.0 s），模型只占约 0.12 s。

改为：
- 开始时配置传感器、开流、预热各一次；之后循环 `DQBUF → 检测 → 输出 DET → QBUF`，不再每帧重启。
- 保留现有防护：GPIO4 毛刺过滤、帧长度与帧头校验、寄存器回读核对（只在开流前做一次）。
- 实测频率：关闭预览 6.14 次/秒，每 10 帧一张预览 6.00–6.02 次/秒；每轮约 166 ms = 颜色转换约 33 ms + 推理约 118–122 ms + 等帧约 13 ms。进一步提速应先优化颜色转换（例如直接在缩放后的 224×224 上转换），模型本身已是官方水平。
- 预览图改为可选：默认不发；需要时按“每 N 帧一张”或按需请求发送。

### 3.2 姿态取帧（JPEG）

- 使用已在依赖中的 `esp_new_jpeg`；编码器直接支持 `JPEG_PIXEL_FORMAT_CbYCrY`（即传感器输出的 UYVY），无需先转 RGB。
- 原图 240×320，4:2:0，质量默认 80（`cam_test quality N` 可改，10–95），旋转交给电脑端做（编码器的旋转只支持 YUYV + 4:2:0）。
- 实测（P2）：每帧约 14.9 KB（14.7–16.7 KB），编码 33.2 ms；编码和发送在单独的低优先级任务里，检测循环只复制一帧（150 KB）后继续，检测频率保持 6.06–6.2 次/秒。
- JPEG 头带帧号、采集时间、尺寸、字节数、FNV32 校验、质量、编码耗时和触发原因（`preview` / `snap`）；该帧的检测框不放在头里，由电脑按帧号对上同一帧的 `DET`。

### 3.3 触发策略

两种来源，均可开关：
- **电脑请求**（✅ 已实现）：电脑发 `snap` 命令，板子发下一帧 JPEG（网页“拍一张做姿态”按钮）。
- **定时**（✅ P2 现用）：`preview N` 每 N 帧发一张，网页默认每 10 帧（约 1.6 秒）。
- **端侧自动**（⏳ P3）：画面中有人、主检测框连续若干帧稳定（中心位移小于阈值），且距上次发送超过 T 秒（默认 3 s，可配置）。

### 3.4 去掉端侧姿态模型

- 不再调用 `pose_engine_init()`，从构建中移除 `coco_pose` 依赖，释放约 0.9 MB PSRAM，启动快约 0.3 s。
- 分区表暂不改动（`coco_pose` 分区保留不写），避免重写分区表；确认稳定后再单独决定是否回收 3.2 MB flash。

### 3.5 命令（串口，与现有 `cam_test` 风格一致）

| 命令 | 作用 | 状态 |
|---|---|---|
| `cam_test stream_start` / `stream_stop` | 开始/停止连续检测 | ✅ |
| `cam_test snap` | 发下一帧 JPEG（需在连续检测中） | ✅ |
| `cam_test preview <N>` | 每 N 帧发一张完整画面 JPEG，0 为关闭 | ✅（P1 时为十六进制缩略图，P2 改为 JPEG） |
| `cam_test quality <N>` | JPEG 质量 10–95，默认 80 | ✅ |
| `cam_test pose {json}` | 接收电脑端坐姿结论，回 `POSE_RX` | ✅（目前只记录，不驱动动作） |
| `cam_test auto_snap <秒>` / `auto_snap 0` | 开启/关闭自动触发及间隔 | ⏳ P3 |
| `cam_test calib` | 记录端侧基线（检测框面积、上沿、高度），由电脑端“校准坐姿”同时下发 | ⏳ P3 |
| `cam_test status`、`rotate*`、`stop` | 保留 | ✅ |

### 3.7 串口输入（P2 修复）

板子原本直接从 128 字节的 UART 硬件 FIFO 读命令，读命令的任务优先级最低，检测和 JPEG 编码占满两个核时读不及，电脑连发两条 `pose` 就会丢字节、被当成无效命令。改为安装 UART 驱动（2 KB 中断缓冲），并在电脑端限制每 30 ms 最多发一条；实测连发 5 条一组、共 40 条全部正确解析，检测频率不受影响。被拒的命令只作警告，不再中断画面流。

### 3.6 端侧状态判断（A 类，规则）

端侧根据连续检测结果维护 4 种状态，电脑离线时照常工作，状态变化时立即上报，平时每秒上报一次。规则与默认阈值见第 6.1 节。端侧只用检测框，不需要关键点，计算量可忽略。

## 4. 通信协议（USB 与 WiFi 共用）

### 4.1 消息

| 方向 | 类型 | 内容 |
|---|---|---|
| 方向 | 类型 | 内容 | 状态 |
|---|---|---|---|
| 板→电脑 | `DET` | `{"seq","t_ms","width","height","rotation","prep_ms","infer_ms","cycle_ms","people":[{"score","box":[x0,y0,x1,y1],"center":[x,y]}]}` | ✅ |
| 板→电脑 | `JPEG` | 头：`{"seq","t_ms","w":240,"h":320,"bytes","fnv32","quality","enc_ms","reason"}`，随后是 JPEG 数据 | ✅ |
| 板→电脑 | `STREAM_STATS` | 每 5 秒：有效帧、坏帧、出队失败、检测次数、发图张数、跳过张数、PSRAM 余量 | ✅ |
| 板→电脑 | `POSE_RX` | 收到 `POSE` 后的回执：帧号、状态、等级、是否过期、累计条数 | ✅ |
| 板→电脑 | `PRESENCE` | 端侧状态（第 6.1 节），状态变化时立即发，平时 1 次/秒 | ⏳ P3 |
| 电脑→板 | 命令 | 见 3.5 | ✅ |
| 电脑→板 | `POSE` | 电脑端姿态判断结果（第 6.2 节），每次姿态推理后发送一条，供台灯动作使用 | ✅ |

`PRESENCE` 示例：

```json
PRESENCE {"seq":1520,"t_ms":845100,"present":true,"sit_s":2710,
          "states":{"away":false,"sedentary":"watch","too_close":"ok","standing":false},
          "calibrated":true}
```

`POSE`（电脑→板，已实现）只发板子需要的字段，紧凑 ASCII JSON，作为串口命令发出：

```
cam_test pose {"seq":1518,"state":"head_down","level":"alert","duration_s":42,"events":["stretch"]}
```

板子回执：

```
POSE_RX {"seq":1518,"state":"head_down","level":"alert","stale":0,"count":71,"latest_seq":1520}
```

- `seq`：该结果对应的端侧帧号；比已收到的更旧时 `stale=1`。
- `state`：主状态，取值见 6.2（另有 `normal`、`unknown`、`not_calibrated`、`no_person`）；`level`：`ok` / `watch` / `alert` / `unknown`。
- `events`：瞬时事件（目前只有 `stretch`），不参与主状态。
- 完整判断（四项各自等级 `levels`、指标 `metrics`、说明文字）留在电脑端，网页和 `GET /api/state` 可见；需要时再加进 `POSE`。
- 字段名固定为英文代码，中文只在网页显示。

`seq` 为板端帧序号，`DET` 与 `JPEG` 通过 `seq` 对齐；电脑端拒绝序号、尺寸或校验不匹配的数据，不用旧图冒充新画面（沿用现有网页的原则）。

### 4.2 USB 通道（默认）

- 物理链路：板载 CH343 USB 转串口，当前 921600 波特率（实测吞吐约 92 KB/s）。
- 该串口同时输出系统日志，因此**不直接混发裸二进制**。第一版用文本行封装：
  - `DET {json}` 一行；
  - `JPEG_BEGIN {header}` → 多行 `JPEG_DATA <offset> <base64>`（每行 144 字节原数据）→ `JPEG_END <seq> <bytes> <fnv32>`。
- 两个任务同时打印会把一行切开交错（标准输出无缓冲，一次 printf 会分多次写出），所以每行先格式化好再一次写出。
- base64 比原数据多 33%（P1 的十六进制方案多 100%）。实测从板子拍下到电脑收完平均 358.6 ms（含编码 33 ms 与串口传输，时钟对齐为估算）。
- 后续优化（实测稳定后再做）：提高波特率到 2M/3M（芯片支持，本板走线未验证）；或传图期间暂停日志、改用带帧头和 CRC 的二进制帧。

### 4.3 WiFi 通道

- 板子作为 STA 连接同一局域网，作为**客户端**主动连电脑服务（电脑地址通过配置或 mDNS 获得），不在板上开放服务端口。
- 连接方式：WebSocket 一条长连接；`DET` 用文本帧，`JPEG` 用二进制帧（头部 JSON + 数据），命令走反向文本帧。
- WiFi 凭据和电脑地址在本地配置后存 NVS，不进代码、不进仓库。
- 断线自动重连；WiFi 不可用时板子照常检测（跟随不受影响），电脑端姿态暂停。
- 注意：现有台灯固件的网络部分不是可用的 LJYD 语音/动作桥，本通道独立实现，不依赖它。

### 4.4 通道选择

- 默认 USB；电脑端服务同时监听两条通道，以最先建立且校验通过的为当前通道。
- 板端配置项 `transport = usb | wifi`，默认 `usb`；切换不改变消息格式。

## 5. 电脑端设计（“云端”）

在 `pose/live/host/` 扩展，网页沿用 `pose/live/web/`。

已实现的模块：

| 文件 | 作用 |
|---|---|
| `pose/live/host/live_pose.py` | 串口连续检测流解析（`DET`、`JPEG`、`POSE_RX`、`STREAM_STATS`），命令队列按 30 ms 间隔发出并记入日志 |
| `pose/live/host/pose_pc.py` | 解码 JPEG、旋转、YOLO26-pose 推理；按与板端主检测框的 IoU 选出目标人物（找不到时取最大的人） |
| `pose/live/host/posture_states.py` | 坐姿规则 5–9（第 6.2 节），输出状态码 + 等级 + 指标；生成回传板子的 `cam_test pose` |
| `pose/live/host/scene_test.py` | 场景准确度测试：按场景统计检出率、误报率、置信度、框中心抖动、离开/回来反应时间 |
| `pose/live/host/web_camera.py` | 本机网页服务；姿态推理在单独线程运行，只处理最新一帧，串口读取从不等它 |

- 环境：项目内 `.venv`（本机只有系统 Python 3.9），Ultralytics 8.4.194、PyTorch 2.8（Apple GPU 可用）、OpenCV、pyserial；模型文件放 `pose/live/models/`，已设为不进 Git。
- 模型：默认 `yolo26s-pose`，Apple GPU；`yolo26m-pose` 已下载可切换。本机用板子真实画面实测见第 7 节。
- 处理流程：接收 JPEG → 校验 → 解码 → 按 `rotation` 旋转 → YOLO26-pose（整帧）→ 选目标人物 → 坐姿规则 → 更新网页 → 回传 `POSE`。
- 端到端计时：用每条 `DET` 的到达时间与板端时间之差的最小值，把板端时钟换算到电脑时钟；会把串口延迟算进去，结果略偏大。
- 校准：网页“校准坐姿”目前只做电脑端关键点基线（3 次有效结果）；向板子下发 `cam_test calib` 随板端状态 1–4 在 P3 做。
- 原 `posture.py` 保留给“姿态关键点（慢）”的板端模式使用。
- ⏳ 未做：关键点 JSONL 记录与“判对了 / 判错了”标注按钮；`WifiTransport`（P4）。
- 网页（已实现）：
  - 画面：240×320 JPEG + 板端检测框 + 电脑端骨架，左上角“云端坐姿判断”；
  - 检测数据：板端检测频率、推理延迟（本帧/平均）；
  - “电脑端姿态 · YOLO26”卡片：模型与设备、推理、解码、板端编码、JPEG 大小、拍下到电脑收到、电脑处理、端到端、板子回执；
  - “检测准确度测试”：五个场景按钮、离开/回来标记、每段时长提醒、结果表、保存到 `pose/live/evidence/scene-test-*.json`；
  - 坐姿卡片：校准与四项等级。

## 6. 坐姿状态定义（摄像头正对用户）

所有阈值都是**暂定值**，需要用 P2 起积累的真实数据调整；没有一项经过验证，不构成医学判断。

### 6.1 端侧状态（A 类，只用检测框）

| # | 代码 | 状态 | 规则（暂定） | 输出 |
|---|---|---|---|---|
| 1 | `away` | 离座 / 回来 | 连续 10 s 无人判为离座；离座后连续 3 s 有人判为回来 | 布尔值 + 状态变化事件 |
| 2 | `sedentary` | 久坐 | 有人状态累计计时；离座 ≥ 2 min 才清零（短暂离开不算休息）；≥ 40 min 为 `watch`，≥ 45 min 为 `alert` | `sit_s` + 等级 |
| 3 | `too_close` | 离太近 | 主检测框面积 ≥ 基线的 1.5 倍，持续 10 s 为 `alert`，未满 10 s 为 `watch` | 等级 |
| 4 | `standing` | 起身站立 | 主检测框上沿上移超过基线框高的 20%，或框上沿贴住画面顶部且框高明显增大，持续 2 s | 布尔值 |

- “主检测框”：置信度最高且与上一帧主框 IoU 最大的框；多人同时出现时只跟踪主框。
- 3、4 需要基线（`cam_test calib`）；未校准时只输出 1、2。
- 起身站立和凑近镜头都会让框变大，可能互相混淆，需实测后调整规则。

### 6.2 电脑端状态（B 类，YOLO26-pose 关键点）

指标都以肩宽归一化，并与个人校准基线比较。

| # | 代码 | 状态 | 依据的关键点 | 规则（暂定） |
|---|---|---|---|---|
| 5 | `head_down` | 低头 | 鼻子、双肩 | 鼻子相对双肩中点的下降量比基线多 0.15 倍肩宽（现有 `head_drop`） |
| 6 | `head_tilt` | 歪头 | 双眼（缺失时用双耳） | 两点连线角度与基线相差 > 12° |
| 7 | `shoulder_tilt` | 肩膀一高一低 | 双肩 | 双肩高度差与基线相差 > 0.12 倍肩宽（现有 `shoulder`） |
| 8 | `stretch` | 伸懒腰 / 举手 | 双手腕、鼻子 | 双手腕都高于鼻子 0.3 倍肩宽以上；瞬时事件，触发后 10 s 内不重复 |
| 9 | `head_on_desk` | 趴桌 | 鼻子、双眼、双耳、双肩 | 鼻子降到双肩连线附近或以下，或脸部 5 个点中有 3 个以上缺失而双肩仍可见；持续判定同下 |

等级与防抖（5、6、7、9，沿用现有逻辑）：
- 指标偏离基线即为 `watch`；连续偏离 ≥ 30 s 且累计 ≥ 3 次有效结果为 `alert`；回到基线范围立即为 `ok`。
- 无法判断（无人、多人、双肩缺失或靠近边缘、未校准）为 `unknown`，并清空计时；方向改变需重新校准。
- 主状态优先级：`head_on_desk` > `head_down` > `head_tilt` > `shoulder_tilt`；同等级时取持续最久的；全部 `ok` 时主状态为 `normal`。
- 现有的躯干侧倾指标（`torso`）保留在 `metrics` 中，但不作为状态：坐在桌后通常看不到髋部。

### 6.3 规则与训练的分工

| 状态 | 方案 |
|---|---|
| 1–4（端侧）、5 低头、6 歪头、7 肩膀一高一低、8 伸懒腰 | 长期使用规则 |
| 9 趴桌 | 先用规则；若误判明显（与低头的边界最模糊），用积累的关键点和标注训练小分类器替换这一类 |

训练条件：某类有数百条人工标注、且规则的误判已有数据证明。训练输入是归一化后的关键点坐标和指标（不是图片），模型为决策树或小型 MLP，在电脑上训练，只替换对应状态，其余继续用规则。

## 9. 风险

- **画质是姿态效果的上限**：240×320、偏粉/过曝；换更大的模型也无法弥补。若 P2 后坐姿判断不可靠，优先修色调。P2 的全分辨率 JPEG 颜色看起来接近正常，没有早期缩略图那样明显偏粉，换场景后需再确认。
- **摆位决定能不能判**：镜头必须拍到脸和双肩；离镜头太近时双肩出画，坐姿规则全部“无法判断”。第一次场景测试就因此作废。
- **板端检测对近距离半身有漏检**：正对镜头坐近时，最近 60 帧里 46 帧检出（PedestrianDetect 训练对象是行人）；准确度测试会给出具体数字。背景里的人也会被检出。
- **串口与日志共用**：传图期间日志插入会打断数据；第一版靠文本封装加校验兜住，必要时传图期间降低日志级别。
- **连续开流的稳定性**：之前的出图故障与接线接触有关，长时间连续取帧需重新验证（P1 验收含 10 分钟稳定性）。
- **WiFi 与摄像头并行**：内存和供电压力增加（可能出现欠压复位），P4 需观察 PSRAM/内部 RAM 余量与复位日志。
- **YOLO26 在本场景的实际优势未验证**：P2 用同一批真实 JPEG 对比 `yolo26s` 与 `yolo26m`，必要时再对比 YOLO11。
- **正对视角的局限**：看不出身体前后方向的变化，驼背、含胸、头前伸、后仰不在本方案中；低头只是近似。
- **端侧框规则相互混淆**：离太近与起身站立都会让框变大；离座判定受检测漏检影响，需要时间防抖。
- **阈值全部暂定**：在积累真实标注前，误判率未知；网页需明确提示“实验功能”。
